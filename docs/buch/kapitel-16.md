# 16. Prozesse dokumentieren und Arbeitsanweisungen erstellen

„Die gültige Datei legt normalerweise Frau König ab. Wenn sie nicht da ist, macht es jemand aus dem Team.“ Dieser Satz erklärt, warum eine technische Suche allein Nordtals Problem nicht lösen kann. Die Ablage braucht einen klaren Ablauf. Solange Veröffentlichung, Freigabe und Vertretung unbestimmt bleiben, findet eine bessere Suche möglicherweise nur schneller die falsche Version.

Prozessdokumentation wird häufig aufgeschoben, weil sie nach zusätzlicher Büroarbeit aussieht. Ein Skill kann die verstreuten Beschreibungen ordnen und gezielte Rückfragen vorbereiten. Seine wichtigste Grenze bleibt: Er weiß nicht von selbst, wie tatsächlich gearbeitet wird. Ein professionell formulierter Sollprozess kann sonst unbemerkt als Beschreibung des heutigen Ablaufs erscheinen.

## 16.1 Der ausgewählte Skill

„process-doc“ aus „knowledge-work-plugins“ ist für die Dokumentation von Geschäftsprozessen vorgesehen. Er strukturiert Zweck, Umfang, Verantwortlichkeiten, Schritte, Ausnahmen und Messgrößen. Eine Zuordnung nach RACI unterscheidet Ausführung, Ergebnisverantwortung, fachliche Beteiligung und Information. Quelle K16 enthält den Originalnachweis.

Bei verbundenen Wissenssystemen sieht die Anleitung auch die Suche nach bestehenden Dokumentationen und eine Veröffentlichung vor. Für das Buchbeispiel erstellen wir einen getrennten Entwurf. Die fachliche Bestätigung erfolgt durch Personen, die den Prozess ausführen und verantworten. Erst danach kann eine Arbeitsanweisung freigegeben werden.

Der Baustein eignet sich besonders für wiederkehrende Abläufe mit Übergaben oder Ausnahmen. Wenn eine Aufgabe vollständig individuell ist, kann eine Fallbeschreibung hilfreicher sein als eine starre Standardanweisung.

## 16.2 Den heutigen Ablauf erfassen

Für Nordtal betrachten wir das Bereitstellen einer neuen Preisliste. Die Eingaben bestehen aus einem Gespräch mit der zuständigen Mitarbeiterin, einer Beschreibung durch ihre Vertretung und einem anonymisierten Beispielvorgang. Wir fragen nach dem Auslöser, den verwendeten Unterlagen, der Freigabe, dem Ablageort und dem Umgang mit einer ersetzten Version.

In der Beschreibung von Frau König wird die alte Datei in ein Archiv verschoben. Die Vertretung überschreibt dagegen gelegentlich die Datei am bisherigen Ort. Diese Abweichung gehört in die Dokumentation. Der Skill darf nicht entscheiden, welches Vorgehen „wahrscheinlich richtig“ ist.

Lassen Sie zunächst einen Ist-Entwurf mit gekennzeichneten Widersprüchen erstellen. Verbesserungen kommen in einen getrennten Abschnitt. Damit bleibt nachvollziehbar, welche Regeln heute gelten und welche erst beschlossen werden müssen.

## 16.3 Die entscheidenden Rückfragen

Ein brauchbarer Entwurf macht fehlende Angaben konkret. Wer bestätigt die inhaltliche Richtigkeit? Woran erkennt eine Vertretung diese Freigabe? Was geschieht, wenn eine neue Datei unvollständig ist? Wie erfahren die Nutzer, dass eine bisherige Version ersetzt wurde?

Begrenzen Sie die ersten Rückfragen auf die Stellen, an denen eine andere Person den Ablauf nicht sicher ausführen könnte. Eine lange Liste allgemeiner Prozessfragen kann die Mitarbeitenden überfordern. Die Dokumentation soll ihre Erfahrung aufnehmen, nicht durch ein Formular verdrängen.

Im Beispiel fehlt vor allem eine eindeutige Freigabekennung. Der Skill kann diesen Bedarf benennen. Ob Nordtal dafür ein Feld, einen dokumentierten Freigabeschritt oder ein vorhandenes System verwendet, ist eine organisatorische und technische Entscheidung.

## 16.4 Aus der Beschreibung wird eine Arbeitsanweisung

Nach der Klärung werden die bestätigten Schritte ausformuliert. Jeder Schritt erhält einen Auslöser, eine ausführende Rolle, eine Handlung und ein sichtbares Ergebnis. „Preisliste prüfen“ genügt nicht. Die Anweisung muss sagen, gegen welche Unterlage geprüft wird und wie eine Abweichung behandelt wird.

Für den Übungsfall beschließt Nordtal folgenden Sollablauf: Die Fachverantwortliche bestätigt Inhalt und Gültigkeitsbeginn. Die Ablageverantwortliche veröffentlicht die freigegebene Datei am vereinbarten Ort. Die bisherige Version wird nachvollziehbar als ersetzt gekennzeichnet. Anschließend wird die Verknüpfung aus einer normalen Nutzerperspektive geprüft. Diese Regeln sind fiktive Beispielentscheidungen.

Die Ausnahme lautet: Fehlt die fachliche Freigabe, wird die neue Datei nicht als gültige Fassung veröffentlicht. Die ausführende Person fragt bei der Fachverantwortlichen nach. Bei Abwesenheit greift die dokumentierte Vertretungsregel. Der Skill soll diese Ausnahme genauso ausführbar beschreiben wie den Normalfall.

Eine RACI-Zuordnung kann hier helfen, wenn mehrere Rollen beteiligt sind. Halten Sie sie klein. Für jeden wichtigen Schritt muss insbesondere klar sein, wer das Ergebnis verantwortet. Eine Matrix mit vielen Beteiligten, aber ohne eindeutige Entscheidungskompetenz löst den Konflikt nicht.

## 16.5 Der praktische Lesetest

Lassen Sie eine nicht am Entwurf beteiligte Person einen fiktiven Vorgang anhand der Anweisung durchgehen. Sie soll jede Stelle markieren, an der sie fragen müsste. Dabei wird häufig sichtbar, dass ein Begriff wie „übliche Ablage“ nur für erfahrene Beschäftigte eindeutig ist.

Testen Sie danach einen Ausnahmefall: Die neue Datei liegt vor, aber die Freigabe fehlt. Der Ablauf muss zu einer Klärung führen. Wenn die Testperson trotzdem veröffentlichen würde, ist die Anleitung nicht präzise genug oder die technische Gestaltung unterstützt den vorgesehenen Prozess nicht.

Prüfen Sie auch den Abschluss. Eine Aufgabe ist erst fertig, wenn die gültige Fassung für die vorgesehenen Nutzer auffindbar ist. Das bloße Speichern im richtigen Ordner kann dafür unzureichend sein, etwa wenn ein veralteter Verweis weiter genutzt wird.

## 16.6 Die Dokumentation aktuell halten

Geben Sie dem Dokument eine verantwortliche Rolle, einen Versionsstand und einen Anlass zur erneuten Prüfung. Eine neue Software, eine geänderte Freigabe oder wiederkehrende Rückfragen können solche Anlässe sein. Ein starres jährliches Datum allein verhindert nicht, dass eine Anleitung zwischenzeitlich falsch wird.

Bewahren Sie Änderungsgründe auf. Wer später eine Regel streicht, sollte erkennen können, welches Problem sie lösen sollte. Der Skill kann aus einer bestätigten Änderung eine überarbeitete Fassung vorbereiten und Unterschiede zusammenfassen. Die sachliche Entscheidung wird dadurch nicht automatisch getroffen.

## 16.7 Was das für Ihre Rolle bedeutet

### Für Geschäftsführer

Priorisieren Sie Abläufe, bei denen Unklarheit spürbare Folgen hat: fehlerhafte Kundeninformationen, lange Übergaben oder Abhängigkeit von einzelnen Personen. Dokumentation lohnt sich besonders dort, wo sie Verantwortung und Vertretung konkret klärt.

### Für IT-Leiter

Vergleichen Sie die Arbeitsanweisung mit den tatsächlichen Möglichkeiten der Systeme. Wenn ein vorgeschriebener Freigabestatus technisch nicht erkennbar ist, braucht es eine passende Umsetzung. Der Text darf keinen Kontrollschritt vortäuschen, den niemand ausführen kann.

### Für Selbstständige

Dokumentieren Sie zuerst wiederkehrende Übergaben an Kunden oder Mitarbeitende. Eine gut beschriebene Übergabe verringert Rückfragen nach Projektende. Halten Sie den Umfang so, dass Sie die Anleitung bei Änderungen tatsächlich pflegen können.

### Für Abteilungsleiter

Lassen Sie Normalfall und Vertretungsfall von unterschiedlichen Personen prüfen. Gerade in Ausnahmen zeigt sich, ob die Arbeit verständlich beschrieben ist. Nutzen Sie Rückfragen aus dem Alltag als Hinweise für die nächste Überarbeitung.

## 16.8 Ihr erster Einsatz

Wählen Sie einen Ablauf mit höchstens wenigen wesentlichen Übergaben. Erfassen Sie einen normalen Vorgang und eine häufige Ausnahme. Lassen Sie daraus eine erste Anweisung erstellen und führen Sie den Lesetest durch.

Messen Sie später, ob Rückfragen und fehlerhafte Übergaben zurückgehen. Die Zahl dokumentierter Seiten ist keine sinnvolle Erfolgsgröße. Eine kurze, angewendete Anleitung kann mehr leisten als ein umfangreiches Handbuch, das niemand im entscheidenden Moment findet.
